# 方案设计

## 一、为什么不用 LangChain / Dify

### LangChain：pydantic v1/v2 混装不可用

早期原型使用 LangChain，撞上版本兼容问题 —— `langchain` 0.2.x 内部依赖 pydantic v1，
而 `langchain-core` 0.3.x 起改用 pydantic v2，两者混装时：

```
RuntimeError: no validator found for <class 'langchain_core.language_models.base.BaseLanguageModel'>
UserWarning: Mixing V1 and V2 models is not supported. `BaseLanguageModel` is a V2 model.
```

炸点在 `langchain/memory/__init__.py` 导入的 `ConversationSummaryMemory` ——
我们根本没用它，但 `from langchain.memory import X` 会执行整个包的 `__init__`，被连坐。
同一条依赖链上的 `langchain_openai` 0.1.x 甚至无法完成 import：

```
PydanticUserError: The `__modify_schema__` method is not supported in Pydantic v2.
                   Use `__get_pydantic_json_schema__` instead in class `SecretStr`.
```

**结论**：只要 langchain 与 langchain-core 跨了 pydantic 主版本，整套都不可用。
最终改用 `openai` SDK 直连（OpenAI 兼容协议），依赖链最短。

附带好处：上下文如何拼装全部显式写在代码里，读代码就能看懂 prompt 是怎么组织的，
不必去翻框架的封装层。

### Dify 等低代码平台：技术栈错位

交付要求是「提供 Dockerfile，能通过容器启动完整服务」，并且要能被别人从零跑起来。
用平台方案意味着要自部署整套（PostgreSQL + Redis + 向量库 + api + worker + web 等约十个容器），
复现成本远高于交一个几百行的应用镜像。

更实际的问题：四条必做里有两条的核心是**数据落到关系型数据库再查出来**，
而平台的知识库是私有向量库，写外部 SQLite 反而要绕 HTTP 节点。
更关键的是工作流定义存在平台数据库里，导出后拿不到任何 Python 工程结构 ——
代码评审这件事根本无从谈起，也看不出真实的开发过程。

题目真正考的是自建能力：有没有针对场景做**约束与调优**、遇到模型能力边界时
怎么绕过去。套平台会把这两件事一起省掉，也就省掉了项目本身的价值。

## 二、关键设计决策

### 1. LLM 的职责边界

只做两件事：① 解释知识点 ② 非结构化 → 结构化 JSON。

统计、判分、分级规则全部是 SQL/Python。理由：LLM 参与的环节越多，结果越不可复现 —— 同一个问题点两次给出不同答案是常态，
统计类功能一旦不可复现就失去意义；同时 token 成本也会失控。

### 2. 知识点库从错题里长出来 🔴

这是本项目最核心的设计。

| 层级 | 来源 | 数量 | 作用 |
|---|---|---|---|
| 第一层：章节 | 一次性写死（教材目录级） | 15 | 归类抽屉的标签 |
| 第二层：具体知识点 | 系统在问答/归类时自动新建并挂靠 | 随使用增长 | 细节内容 |

为什么不预先穷举：高数几十个定理公式人工列不完，而且学生只问了几道题却准备几十个知识点，
覆盖率毫无意义。题目要的是"针对薄弱点闭环"，而薄弱点只能从真实错题里积累。

为什么必须有顶层边界：不给上限，AI 会造出「极限」「函数极限」「求极限」「洛必达」
这种粒度混乱的并列条目，那时"哪个知识点最薄弱"就没有答案，掌握度统计作废。

配套约束：`find_or_create()` 的顺序是精确名字匹配 → 包含关系与关键词重叠 →
命中就复用 → 都没命中才创建。跳过查重会导致同义条目并存。

### 3. 三级容错策略

```
校验通过 → 采用
校验失败 → 带原因回喂重试（最多 2 次）
仍失败   → 降级为人工填写，主流程不中断
```

需求本身就写明「识别结果允许用户确认或修正后再入库」，所以降级路径是设计的一部分，不是妥协。
把失败原因一起发给模型，比盲目重问成功率高得多。

### 4. 掌握度是估计值

🔴 分级规则写进 SQL 的 CASE WHEN，不调用大模型 —— 可复现、零成本，
而且任何人问「这个知识点为什么算未掌握」，都能直接指出是哪几行在起作用。

```
掌握度 = 基础正确率 × 难度加权系数 × 时间衰减系数
```

- 难度加权：全易题 1.0 / 含中等 1.05 / 含难题 1.15
  （封顶的是**最终掌握度**截断在 1.0，不是难度系数本身）
- 时间衰减：≤7 天 1.0 / 8~30 天 0.9 / >30 天 0.75
- 分级阈值：<40% 未掌握 / <70% 基本掌握 / ≥70% 已掌握 / 练过 <3 次 样本不足

排序三级键：NULL 沉底 → 档位序（未掌握→基本掌握→已掌握→样本不足）→ 同档内升序。
「样本不足」不参与"最薄弱"排名，否则新知识点会永远霸榜、练习一直推没人练过的题。

对应官方加分项「按知识点给出掌握度估计」。

### 5. 练习优先用题库而不是生成

生成的题目需要额外校验"能不能客观判定对错"，成本高且不稳定。
本地题库的题经过人工确认，抽题只是按薄弱点加权随机。
只有题库覆盖不足时才调用模型，且必须通过"可客观判定"校验才采用。

### 6. 开场白不进对话历史

多数模型服务的 chat template 不接受以 assistant 开头的消息序列：

```
Error rendering prompt with jinja template: "No user query found in messages."
```

Streamlit 每次交互都会从头重跑脚本，如果开场白存在对话历史列表首位，
首轮请求就可能带上它触发报错。现在的做法是开场白单独渲染、不写入历史，
保证发给模型的 payload 恒为 `[system, user, ...]`。

## 三、分层架构

| 层 | 文件 | 唯一职责 | 硬性规矩 |
|---|---|---|---|
| 界面 | `streamlit_app.py` | 展示与交互 | 🔴 不含业务逻辑、不发网络请求、不写 SQL |
| 业务 | `qa.py` / `intake.py` / `profile.py` | 功能编排 | 不写 SQL、不拼原始 prompt |
| 能力 | `llm_client.py` | 模型调用 | 🔴 全项目唯一发网络请求处 |
| 约束 | `prompts.py` / `schemas.py` | 提示词与校验 | 所有 prompt 集中管理 |
| 数据 | `db.py` / `knowledge.py` / `schema.sql` | 持久化与挂载 | 🔴 唯一碰数据库处，SQL 一律参数化 |

价值：换模型供应商时只改 `.env` 三个变量，其余一行不动。

## 四、刻意不做的事

| 决定 | 理由 |
|---|---|
| 不加登录与多用户体系 | 单人本地应用。加了要处理鉴权、数据隔离、密码存储、会话管理，全是与题目无关的工作量 |
| 不做 RAG 教材引用 | 官方加分项而非必做，且需要额外的文档解析、切块、向量库运维三项工作 |
| 不用 ORM | 五张表几条查询，裸 SQL 更透明，也让组员更容易看懂 |
| 不用前端框架 | Streamlit 纯 Python，五台机器几分钟装好 |

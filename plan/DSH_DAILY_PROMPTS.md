> **怎么用**：找到自己负责的那一段，整段粘给你的 AI。第一次先发第 0 节背景。
>
> 🔴 **所有任务通用两条规矩**（不用每个框都写一遍，AI 会记住同一会话里的要求）：
> ① 先列方案给我看，我确认后你再动手改文件；一次只动这个任务涉及的文件。
> ② 跑通之后逐段用大白话解释这段代码，然后出 3 道题考我。

## 0. 项目背景（第一次对话必发，之后不用重复）

```text
请记住以下项目背景，后面所有任务都基于它。

【项目】学习辅导 AI 助教，限定学科「高等数学」（同济教材章节体系）。5 人小组开发，各用各自电脑，
通过 GitHub 同步，按步骤推进（不按日历，做完一步才进下一步）。代码主要由你（AI 助手）编写，
但每个组员必须能看懂并解释自己负责的那一层，答辩时可能被要求现场改代码。

【四个功能板块】
  ① 知识点问答：学生问概念，给出结构化讲解；只回答本课范围内的问题
  ② 错题录入：手输或拍照上传做错的题，自动识别题干、归类知识点、判断错因，
     用户确认后入库
  ③ 掌握度分析：统计每个知识点的正确率，标出薄弱点
  ④ 针对性练习：按薄弱知识点出题，作答后判分并更新掌握度

【技术栈】严格遵守，不要自行更换：
  Python 3.11 + Streamlit（界面，不用任何前端框架/HTML/JS）
  SQLite（单文件数据库，裸 SQL，不用 ORM）
  openai SDK（走 OpenAI 兼容协议对接模型服务）
  🔴 不使用 LangChain / LlamaIndex 等 AI 框架，直接调用 openai SDK
  Dockerfile 用于交付复现

【代码分层】硬性规矩，不许打穿：
  streamlit_app.py    界面入口，只做展示交互
                      🔴 不含业务逻辑、不发网络请求、不写 SQL
  app/llm_client.py   🔴 全项目唯一允许发网络请求的文件
  app/prompts.py      所有提示词集中在这里
  app/schemas.py      校验大模型返回的 JSON
  app/db.py           🔴 全项目唯一碰数据库的文件，SQL 一律用 ? 参数化
  app/qa.py           功能①
  app/intake.py       功能②
  app/profile.py      功能③④
  app/knowledge.py    🔴 知识点的查找 / 相似度匹配 / 新建挂靠逻辑（C₁）
  app/stubs.py        假实现的桩函数（队友代码没好时先用它跑界面）
  schema.sql          建表语句
  data/chapters.json  🔴 15 个归类抽屉的标签（不是预先建的知识点库，具体知识点运行时生成）
  data/question_bank.json      题库（可先空着，靠真实错题积累）
  seed_data.py        演示数据初始化
  tests/offline_check.py         离线自检脚本
  docs/interfaces.md  🔴 函数契约，跨人协作的唯一依据

【核心设计：知识点库是从错题里长出来的，不是预先穷举的】🔴
  高数几十个定理公式人工列不完，而且学生只问了几道题却准备几十个知识点毫无意义。
  所以采用两级结构：
    第一层 章节（约 15 个，一次性写死，如 ch_function_limit）—— 🔴 归类抽屉的标签，不是内容
    第二层 具体知识点（如"洛必达法则""泰勒展开""分部积分法"）
           🔴 由你在问答和归类时自动新建并挂靠到合适的章节下
  约束：只能在已有的 15 个章节下创建子节点；创建前必须先做相似度检查，
       含义相同或高度重叠的就复用已有条目，不要重复建。

【五条关键约定】
  1. 🔴 知识点的 chapter_id 必须来自预定义章节候选集，绝不允许发明新章节
  2. 🔴 具体知识点可以新建，但必须先查重，避免「不定积分」和「不定的积分」两条并存
  3. 掌握度是估计值 = 基础正确率 × 时间衰减 × 难度加权，分级阈值写在 SQL 里，
     不调用大模型
  4. 你只负责两件事：解释知识点、把非结构化输入转成结构化 JSON。
     统计、判分、分级、去重判断全部是普通 Python + SQL
  5. 单人本地应用，不加登录和多用户体系

【工作方式】组员系统是 Windows + PowerShell，多数人是编程新手。
看不懂时要你用大白话解释清楚。每次改完代码要真的运行一遍贴出真实输出，
不要只说"应该可以了"。一次只改一个文件的事，不要顺手重构其他文件。

确认理解后简要复述关键点，等我布置任务。
```

### B 🔴 本步的关键任务

```text

如果不支持，说明错题录入的拍照路径要改成手输题干。

       validator=None, max_retry=2) -> LLMResult
  vision(prompt_text, images, ...) -> LLMResult
```

### C₂ 🔴 掌握度估计

```text
【任务】实现掌握度查询 mastery_table()，返回 pandas DataFrame，列：
知识点 / 所属章节 / 练习数 / 做对数 / 基础正确率 / 难度加权 / 时间衰减 / 掌握度 / 状态

🔴 掌握度是估计值，不是简单除法：

    掌握度 = 基础正确率 × 难度加权系数 × 时间衰减系数

    难度加权（难题答对更能证明掌握）：
      全易题 → 1.0 / 含中等 → 1.05 / 含难题 → 1.15
    ⚠️ 封顶的是**最终掌握度**（截断在 1.0 = 100%），不是难度系数本身。
       若理解成「先把系数封顶 1.0」，难题加成永远不起作用 —— 与设计意图相反。
    时间衰减（间隔复习逻辑）：
      距上次练习 ≤7 天 → 1.0 / 8~30 天 → 0.9 / >30 天 → 0.75

分级阈值写进 SQL 的 CASE WHEN，不调用大模型：
    练过 ≥3 次 且 掌握度 <40%   → 🔴 未掌握
    练过 ≥3 次 且 掌握度 <70%   → 🟡 基本掌握
    练过 ≥3 次 且 掌握度 ≥70%   → 🟢 已掌握
    练过 <3 次                  → ⚪ 样本不足

⚠️ 这套系数不需要多精确，但必须是**确定性的、可解释的** ——
评审问"为什么这个知识点算未掌握"，你要能当场指出是哪几个数字。
这对应官方加分项「按知识点给出掌握度估计」。

排序三级键，顺序不能调：
  ① 掌握度为 NULL 的排最后
  ② 档位序：未掌握 → 基本掌握 → 已掌握 → 样本不足
  ③ 同档内掌握度升序
理由：界面要显示"最薄弱的知识点"给用户去练。样本不足的排在前面会导致
系统一直推没人练过的题。

其他要求：
  □ 必须 LEFT JOIN，从没练过的知识点也要出现在结果里
    （如果用 JOIN，它们会直接消失，看起来像"数据丢了"）
  □ 除法用 NULLIF 防除零
  □ 排序不要用 NULLS LAST（旧版 SQLite 不支持会报语法错误），
    改用 CASE WHEN xxx IS NULL THEN 1 ELSE 0 END
  □ 补测试：造 3 个知识点，其中一个灌 10 条记录（对 3 条，全是易题），
    断言基础正确率 30.0、状态未掌握；再造一个只有 2 条记录的，
    断言它是样本不足且不排第一；再验证同一批答对记录在"含难题"时掌握度更高

同时实现 weak_points(n)：排除样本不足后取掌握度最低的 n 个（供功能④出题用）。

```

## 附：两条最重要的纪律

**1. 每次让 AI 动手前，末尾带这句**

```text
先列方案，不要直接改文件。
```

价值不在于选对方案，而在于**在它动手前发现它理解错了**。AI 手很快，你说一句它可能改十个文件，工作区和 git 历史都会变乱。

**2. 跑通之后必补这句**

```text
逐段用大白话解释刚才写的代码。标出：
① 哪里调用了外部服务或读写数据库
② 出错会怎样、有没有兜底
③ 哪些数字是规则阈值
然后出 3 道题考我，看我是不是真懂了。
```

成本 30 秒。理由是硬的：官方明说答辩可能现场改代码，而评审给的时间可能是 60 秒。

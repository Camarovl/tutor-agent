# 未完成部分及原因

诚实列出。官方要求 README 覆盖「已验证的功能清单，以及已知的问题与未完成部分」。

---

## 一、明确未做的

### 1. RAG：结合教材/课件并给出引用出处 ❌

**原因**：不是核心闭环的一环，而代价是额外的文档解析、切块、向量库运维三项工作。
四条必做功能优先保证打通。
在时间有限、MVP 四条优先的前提下砍掉。

**若要做**：现有架构预留了位置 —— 新增 `app/rag.py`（本地向量库 + PDF 切块），
在 `qa.answer()` 拼上下文时把检索结果并入 context_block，prompt 结构不用改。

### 2. 多轮追问与澄清 ❌

信息不全时系统直接按已有信息作答，而不是反问"你指的是哪个函数？"。

**原因**：需要状态机管理"待澄清"轮次，复杂度高但演示效果不明显。
当前用「引导式四段结构」替代 —— 即使问题模糊，也会先给定义再给例子，用户能自然接上。

### 3. 报表导出 ❌

掌握度只有页面图表，不能导出 PDF/Excel。技术上加两个按钮即可，优先级排最后。

## 二、做了但有局限的

### 4. 拍照识别准确率依赖模型能力 ⚠️

实测结论：**视觉模型的 OCR 质量差异远大于代码本身的影响**。
弱模型会把 `f(x)=x²-2x+3` 认成 `f(x)=x2-2x+3`，甚至漏读题干后半句。
高数的积分号、极限符号、上下限比简单公式更容易出错。

**应对**：不追求全自动。需求本身写明「识别结果允许用户确认或修正后再入库」，
所以②页有完整的可编辑确认表单；识别失败时降级为空表单让人手工填，主流程不断。

**已知残留**：图片旋转、手写潦草、多题混拍三种情况未做预处理。

### 5. 生成的练习题质量不稳定 ⚠️

模型偶有：选项重复、答案与解析矛盾、超出课程范围。

**应对**：三道防线
1. 优先从本地题库抽题（人工确认过，最可靠）
2. 必须通过"可客观判定对错"校验才采用
3. 校验失败带原因重试，仍失败退回题库现存的题

**已知残留**：校验器只能保证结构合法（答案在选项中、类型正确），
无法判断数学内容是否真的正确。极端情况下可能生成一道题干自相矛盾的题。
彻底解决需要引入符号计算引擎逐题验算，收益与成本不成比例。

### 6. 知识点动态挂载的查重是启发式的 ⚠️

`find_or_create()` 靠精确名字匹配 + 包含关系 + 关键词重叠判断，不是语义相似度。

**后果**：措辞差异大的同义概念仍可能各建一条（如「中值定理」与「拉格朗日中值定理」）。

**权衡**：引入语义相似度需要额外的 embedding 调用，每次归类多一次网络请求和费用。
当前做法配合可编辑确认表单兜底 —— 人能看到归到哪个知识点并改正。

### 7. 无多用户体系 ⚠️（刻意不做）

单用户本地应用，所有人共用一份 SQLite。

**理由**：加了登录就要处理鉴权、数据隔离、密码存储、会话管理 ——
全是与题目无关的工作量，而且会引入密钥管理的新风险。

若要支持多人，最小改造是给三张表加 `user_id` 列并在查询处带上过滤条件。

### 8. 章节骨架的两处非教材项 ⚠️

`data/chapters.json` 里第 15 项「微积分综合应用」**不是教材章节**，是本项目的扩展抽屉，
用于挂跨章节的综合题。它不对应任何教材章节，属于本项目的自定义分类 ——
如果不想为它单独解释，删掉即可，不影响其余 14 章。

另外「微分方程」在教材里是一章，本项目按难度拆成两个抽屉（便于掌握度分层），
这是刻意的设计选择。

## 三、工程层面的已知不足

### 9. 知识点的来源字段无法区分 ⚠️

`knowledge_point.created_from` 目前**固定记录为 `intake`**，无论是从问答链路
（`qa.py`）还是错题归类链路（`intake.py`）创建的知识点，写进去的值都一样。

**影响**：想统计「问答过程中自动长出了多少知识点」时得不到准确数字。
其余功能不受影响 —— 归题、掌握度、练习判分都正常。

**原因**：`find_or_create(name_hint, chapter_id, context)` 没有 `created_from` 参数，
实现里只能写死。若为此改签名，已开工的调用方要跟着改，代价大于收益。

**若要修**：给该函数增加 `created_from: str = "intake"` 参数（放在关键字参数位），
由调用方传 `"qa"` 或 `"intake"`；同时改 `docs/interfaces.md` 第二节。

### 10. `kp_error_distribution()` 未实现 ⚠️

契约第一节曾列过这个函数（错题按知识点分布 + 主要错因），**目前没有任何实现**，
也没人调用 —— 界面上的"错因分布"图还没做。

**影响**：无。掌握度分析用的是 `mastery_rows()`，不依赖它。

**若要补**：由 C₁ 在 `db.py` 里实现（一条 `GROUP BY error_type` 的聚合查询），
C₂ 在 `profile.py` 里组装成 DataFrame，D 加一张图。属于锦上添花，不进必做清单。

### 11. 重试失败的调用未计入成本统计 ⚠️

`llm_log` 的读写都已接通：`llm_client` 每次成功调用后写 `db.log_llm_call()`，
`summary_text()` 读它算出 `llm_calls` / `llm_tokens`。指标卡数字会随使用增长。

**残留偏差**：因校验失败而重试的那几次调用**没有记账**，所以成本会被略微低估。
实测：一次失败 + 一次成功 = 发 2 次请求，`llm_log` 只 +1 条。

**影响**：只影响成本统计的精度，不影响任何功能判断。

**还款条件**：`llm_client` 的重试循环里，每次 `_call_once` 返回后都记一条
（成功 `success=True`、失败 `success=False`），最终放弃时也要落最后一条。

### 12. 测试覆盖不均 ⚠️

`tests/offline_check.py` 覆盖：数据完整性、三条关键 SQL 语义、两种校验器的畸形输入、
判分逻辑、配置缺失时的优雅降级。

**未覆盖**：
- LLM 调用的集成测试（需真实 API，会产生费用且结果不稳定，不适合放进自检脚本）
- Streamlit 界面交互测试（需要 `streamlit.testing.v1.AppTest`，投入产出比低）
- Docker 镜像构建验证

🔴 **第三条必须补做**：找一台装了 Docker 的机器实际 build + run 一次。
容器化交付是要能被别人从零跑起来的，跑不通等于这条没交。

### 13. 调用日志只记 token 不记金额

`llm_log` 表记录了 prompt/completion tokens 和重试次数，但没有换算成钱。
因为各家供应商计价方式不同，硬编码单价容易过时。
答辩时用「累计 X 次调用、输入 Y / 输出 Z tokens」表述，侧边栏已实时显示这组数字。

### 14. 提示词没有版本管理

`prompts.py` 里的文案随迭代修改，历史版本只存在于 git 提交记录中。
更规范的做法是把每次 prompt 变更与对应的评测结果一起记录，便于回答"为什么改成这样"。
目前靠 [issues.md](issues.md) 里的文字说明替代。

### 15. `vision()` 的降级判断依赖错误文本特征 ⚠️

当模型不支持图片时，代码靠匹配报错信息里的关键词决定要不要退回纯文本路径。
这种做法偏脆弱 —— 更稳妥的是由配置显式开关。

保留现状的理由：目前所有已知供应商的报错都包含相关字样，实测可用；
改成配置开关会增加一个需要每人手动设置的项，反而更容易出错。
